# /browser-test — drive a real browser, not a headless mock

The chrome-devtools MCP server gives Claude live access to a real
Chromium instance. Use it when the feature under test:

- **Renders to the DOM** (any React / Vue / Svelte / Django template / Thymeleaf view)
- **Has interactive elements** that JS unit tests can't exercise faithfully
- **Hits real network** (API calls, WebSocket frames, etc.)
- **Cares about accessibility** (keyboard nav, focus order, ARIA, contrast)
- **Has performance budgets** (LCP, CLS, INP, bundle size, runtime stalls)

Unit/integration tests confirm the code does what you wrote;
`/browser-test` confirms the *user experience* matches what you intended.

## Prerequisites

The chrome-devtools MCP server must be registered. Confirm:

```bash
ls .claude/mcp.json | grep -i chrome
# or
claude mcp list 2>&1 | grep -i chrome
```

If not registered, see [docs/observability/](../docs/observability/) for
the install path. The MCP server tools then become available as
`mcp__chrome-devtools__*` in this session.

## How to run

You don't shell out — you call MCP tools directly. The slash command is
a structured prompt for YOU (Claude) to follow.

### Path A — test a specific URL

User provides a URL + optional named scenario:

```
/browser-test https://localhost:5173/cart --scenario "add line item"
```

Walk this checklist:

1. `mcp__chrome-devtools__navigate_page` to the URL
2. `mcp__chrome-devtools__take_snapshot` to capture the DOM tree (cheaper + structured vs screenshot)
3. Run the scenario via `mcp__chrome-devtools__fill_form`, `mcp__chrome-devtools__click`, `mcp__chrome-devtools__type_text`, etc. — keep each step explicit so the user can replay it
4. After each interaction:
   - `mcp__chrome-devtools__list_console_messages` — fail-fast on any new error
   - `mcp__chrome-devtools__list_network_requests` — surface unexpected 5xx, 4xx-not-401-auth, or missing API calls
5. End with `mcp__chrome-devtools__lighthouse_audit` for the perf + a11y score

### Path B — verify a feature was implemented correctly

User describes the feature; you decide what to test:

```
/browser-test --feature "user can soft-delete a cart and recover it within 30s"
```

Build the test plan yourself:
1. Figure out the relevant URL(s) from the codebase
2. Outline the scenario (3-7 steps)
3. Tell the user the plan FIRST, then ask "proceed?"
4. Execute via the same MCP tools as Path A

## Output — structured report

After every run, emit this format:

```markdown
## Browser test — <feature/url>

### Setup
- url:        <final url after redirects>
- viewport:   1280×720 (default; use --emulate for mobile)
- scenario:   <name or autogenerated>

2. [PASS] clicked "Add to cart" — DOM updated, console clean

```

## What to test by feature type

### CRUD forms
- Submit valid input → expect 201 + redirect/toast
- Submit invalid input → expect 422 + field-level error rendered, NOT a generic toast
- Keyboard-only path: Tab through every field; Enter submits; focus visible at each step

### Authentication flows
- Logout → no auth-only routes accessible
- Expired session → graceful redirect to login (not a JS exception)
- "Remember me" → cookie persistence verified via DevTools storage panel

### Real-time / WebSocket
- Open two browser contexts (`mcp__chrome-devtools__new_page`)
- Trigger event in context A → assert visible in context B within 5s
- Disconnect network → assert reconnect happens cleanly

### Lighthouse / Core Web Vitals
- For any feature: run `lighthouse_audit` baseline + after changes
- Block merge if Performance drops > 5 points or Accessibility < 90

## Anti-patterns to avoid

- **Don't take screenshots when you could take a snapshot.** Snapshots
  are structured DOM; screenshots are pixels. The former is reasonable
  to diff; the latter is brittle.
- **Don't test "everything" in one session.** One feature, one scenario.
  Long scripts are flaky and slow to debug.
- **Don't `wait_for` arbitrary timeouts.** Wait for a specific element
  / text — that's resilient to network jitter; sleep is not.
- **Don't ignore console warnings.** Warnings are bugs we haven't named
  yet. Surface every new one in the report; let the user triage.
- **Don't trust the visual.** "It looks fine" with a 422 in the network
  panel is still broken.
